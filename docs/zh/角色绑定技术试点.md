# 角色绑定技术试点

角色模板包含稳定的角色与技能 ID。编排中心在派发前将模板解析为实例。Host 校验冻结结果，并将实例工作流交给现有 workflow-engine SDK。SDK 本身不变。

本试点证明路由与传输行为，不认证网络优化能力，也不为自治代理提供生产准入。

## 角色模板的查看与保存

设计器在打开与保存角色模板或角色/实例混合模板时，保留目录/版本元数据、原任务 ID、角色/技能 ID、绑定组、步骤依赖与上下文引用。导入转换不改变源对象；仅画布使用的属性不会写入保存的 PSOP。

任何包含角色任务的工作流，包括其实例任务，图结构与任务内容均为只读。用户可以选择、查看、移动、缩放节点，并在保存对话框中修改工作流名称、描述与标签。删除、重连边、合并节点、移除代理、清空画布与替换技能被阻止。普通实例工作流保持既有编辑行为。

执行态按原任务 ID 投影到原始角色图。解析出的实例/技能细节单独展示，不取代保存的角色身份。解析证据与结构化拒绝原因在执行时间线中展示。错误仅通过精确的原任务 ID 定位画布步骤；未映射的 SDK 任务 ID 保持为工作流级错误。

角色工作流不能使用当前仅支持实例的沙箱。按钮会说明该限制；直接的沙箱请求在注册表访问或执行调度之前即返回 HTTP 422 与 `ROLE_SANDBOX_NOT_SUPPORTED`。实例沙箱行为不变。显示名来自模板精确目录发布的已批准投影，而 ID 与版本保持可见并用于序列化。若该发布不可用，设计器保留原 ID 并显示提示。保存对话框还提供**下载设计 JSON**，它不依赖目录访问，也无需保存。

## 角色工作流的生成

意图生成与 PreFlow/SOP 生成均支持 `binding: "role"` 与可选的 `catalog_version`。API 请求省略 `binding` 时保持实例生成。前端生成模式默认为角色模式；用户可显式选择实例兼容模式。图构建器保持既有实例编辑行为。既有工作流保持原绑定模式。

角色生成不加载 AgentCard，也不查询实例注册表。它只使用 `role_catalog_path` 中已批准的角色与已批准的技能。不带版本的新请求选择该已配置发布一次；带版本的请求要求精确匹配。既有的保存/执行加载器保持精确版本要求，绝不回退到其他发布。

共享上下文为请求固定发布内容。保存前，服务器再次核对发布版本、内容指纹与批准状态，然后走既有保存处理器与 CatalogGate。即使版本与技能 ID 未变，发布内容变化也会拒绝请求。该检查不提供跨其他发布目录文件的进程的事务；请以不可变方式发布版本文件。

PreFlow 动作获得互不相同的 action ID，包括重复的描述。匹配使用角色/版本/技能联合身份。结构阶段必须恰好一次地保留每个选中任务及其身份。显式实例绑定、未批准技能、错误版本、角色 SelfLoop、重复 ID 与选中任务集变更均被拒绝。不使用回退代理。

经认证的内部只读端点 `GET /rest/v1/orchestrate/role-catalog?catalog_version=<version>` 返回与生成相同的已批准显示投影。它有限流，不暴露路径、来源文档、实例或凭据。它不引入第二个目录存储，也不引入目录管理 API。

HTTP 示例、响应信封与错误码见 [API 参考](编排中心API参考.md)。

生成日志包含请求 ID、入口、绑定模式、目录版本、阶段、耗时与结果/错误码。不记录原始模型输出与业务意图。确定性模型响应与真实本地 Host/worker 传输测试验证的是技术链路，不是模型质量或业务能力。

## 配置

为编排中心配置经评审的精确版本角色目录与实例注册表发布。见 `etc/conf/server.conf.example` 中的注释键：

```properties
role_catalog_path=/protected/releases/catalog.json
role_registry_path=/protected/releases/instances.json
role_execution_scope=operator-a/city-a/ran-domain-a
role_authorized_instances=technical-a,technical-b
```

`role_execution_scope` 是默认值；执行请求可提供具体的 `tenant/site/business_object` 范围。注册表范围元组必须覆盖整个请求元组。`role_authorized_instances` 是部署级授权上限：请求可以收窄但不能放大。它不是按用户的资源 ACL。调用方身份来自认证中间件；调用方自称的 `caller_id` 被忽略。

在编排中心与 Host 进程环境中设置相同的密钥 `ORCH_ROLE_DISPATCH_KEY`，至少 32 字节密钥材料。通过部署的密钥机制注入。它不从 `server.conf` 读取。Host 也接受通过 `HostAgentConfig.role_dispatch_key` 的显式注入，该值不进入配置的 `repr`。

无可用的密钥时，编排中心在创建传输前返回 `ROLE_EXECUTION_NOT_ENABLED`。该默认值不变。启用试点前请同时升级编排中心与 Host。内置角色目录保持草稿状态，不授权执行；测试使用独立的合成已批准夹具。

角色候选可以声明多个接口、完整的认证声明与 required 扩展。当注册端点命中某个声明的 HTTP+JSON 接口、所有声明接口 URL 均为不内嵌凭据的干净 HTTP(S)、且每个认证要求都引用卡片自身声明的 scheme 时，投影接纳该候选；没有匹配 scheme 的要求在选择前被排除。派发时 Host 将 SDK 钉选到选定端点，并执行下述扩展与认证策略。既有实例任务保持原有 SDK 凭据处理，包括登录与 Bearer 注入。真实凭据保存在受保护的凭据引用中，绝不放进 AgentCard 描述、URL、扩展内容、快照或源码库。

## 派发契约

| 元数据键 | 载荷 |
|---|---|
| `__orch_psop_id__` | 选定模板 ID |
| `__orch_psop__` | 实例绑定执行副本 JSON |
| `__orch_binding__` | 版本、范围路径与逐任务绑定证据 JSON |
| `__orch_cards__` | 完整 `role-pilot-v2` 执行信封 JSON |
| `__orch_proof__` | HMAC-SHA256 签名与十进制字符串签发时间 |

签名覆盖全部四个执行字段与原始运行意图。Host 拒绝缺失、被修改、过期（超过 300 秒）或预签发（超过 30 秒）的证明。指纹单独覆盖内容一致性。证明提供认证与新鲜度窗口；它不是恰好一次机制，也不是跨进程防重放机制。

共享类型契约为 `host_agent.role_contract.RoleSnapshot`。编排中心保留其编辑模型，但校验相同的线上规则。未知信封字段、畸形的授权集合与通配执行范围在校验中致命拒绝。每个角色任务必须恰好一个绑定，每个选定实例恰好一张卡片。执行副本只能进行声明的角色到实例替换；图结构与旧任务保持原样。工作流任务 ID、步骤名与绑定组保持 PSOP 长度约束；目录的 1024 字符标识符限制不适用于这些字段。绑定组仍须包含非空白字符。

核对当前注册表中缺失、重复或变化的选定卡片后，Host 从冻结数据重建选定卡片并交给其既有客户端工厂。它绝不用刷新的卡片替换冻结的选定卡片。状态更新使用编排中心执行工作流的独立副本。SDK 接收 `Workflow.from_dict(...)`，其中移除角色专用的编辑字段。旧执行保持既有路径。

对于角色执行，Host 还会推导派发投影：每张选定卡片交给 engine client 时仅保留与注册端点匹配的 HTTP+JSON 接口，使 SDK 基于协议版本的接口选择不会漂移到其他声明端点。冻结快照、指纹与审计证据保留全部声明接口；投影只存在于派发路径。角色任务在派发前还要通过扩展四查：激活的 URI 必须由卡片声明，必须处于受支持集合内（仅 Task-T），required URI 必须被激活，激活的 Task-T 必须携带 `metadata` 载荷。同一四查在下一条请求发出前对每条协商回复内容运行，使控制点不能在交互中途扩大扩展信封；被拒绝的回复保留原任务标识，并经 SDK 的取消清理路径。认证同样前置检查：声明 scheme 与要求的代理需要带有可用登录配置的凭据条目，或注入的 `AuthProvider`。认证要求互为备选——一个完整配置的要求即满足卡片，镜像 SDK 拦截器。有一个组合明确暂不支持：同一 requirement 中多个 scheme 映射到同一大小写不敏感认证头名（直接同名或经配置的 `auth_header` 派生）的组合，会以前置的 `AUTH_METHOD_UNSUPPORTED` 拒绝，因为 SDK 只能通过运行时令牌值裁决这样的组，其最终采用的要求无法预测；若要支持该组合，需要在真实头合并处做大小写不敏感处理，而该合并点位于 SDK 内部。`AuthProvider` 输出仅对需要认证的角色任务校验：同一 requirement 的每个 scheme 必须贡献非空且格式正确的头（Bearer 令牌遵循 `Authorization` 约定，API key 用声明头；头名与 Bearer 前缀大小写不敏感比较），或满足任一备选要求，或携带 Host 配置的自定义头约定。Provider 的输出在进入 SDK 的精确键头合并前，先以大小写不敏感语义合并：同名同值去重为一条，同名异值以 `AUTH_HEADER_CONFLICT` 拒绝；scheme 派生头名被重写为凭据侧实际写入的生效拼写。该拼写镜像 SDK 凭据拦截器采用的要求——每个 scheme 均有可用凭据配置的首个 requirement（配置的 `auth_header` 优先于声明 API key 头名，再优先于 `Authorization` 约定）；被跳过的不完整组中的 scheme 即使已配置也不贡献拼写；无可用组时采用声明拼写。同值去重，异值在 Provider 头与凭据头相遇处触发 SDK 自身的冲突拒绝。旧实例任务与无认证角色任务保持 Provider 既有语义。派发失败与被拒绝的前置检查以 `ROLE_DISPATCH_FAILED` 呈现，携带 `error_details.reason` 判别符与原始执行、任务、实例标识。混合执行中已映射的旧实例任务保持既有派发行为。

## 业务策略上下文

注入的 `control_point_factory` 接收带可选 `role_execution` 值的 `ControlPointContext`。角色执行时，它包含已校验的中心执行 ID、调用方 ID、具体范围与任务绑定。旧工作流时为 `None`。业务策略应从这个已校验上下文获取运行时对象范围，而不是从自由文本或共享全局状态推断。

```python
def create_policy(context):
    execution = context.role_execution
    if execution is not None:
        return MyPolicy(role_execution=execution)
    return MyLegacyPolicy()
```

SDK 自行创建执行与任务 ID。在策略回调内，用 `role_execution.task_identity(request)` 获取原始 PSOP 的 `task_id`、`step_name`、`subtask_index`、`sdk_execution_id` 与 `sdk_task_id`。用 `role_execution.binding_for(request)` 获取该任务的角色绑定；对已映射的旧实例任务或 SelfLoop 任务返回 `None`。未知或外来的执行/任务 ID 抛出 `LookupError`。不要把 SDK 请求 ID 与中心 ID 直接比较，也不要从代理/技能名推断身份。

Host 按精确的步骤与子任务位置映射 SDK 公开的 `task_request` 事件，并等待登记完成后才调用 `on_task` 或 `on_self_task`。这覆盖相同的并发任务而不改变其输入、请求、SDK ID 或事件载荷。本地事件缺失在五秒后超时；不一致的坐标在业务派发前致命拒绝。桥接作用域限于单次执行，并转发路由/协商回调。协商回调可通过 `request.task` 解析其原始任务。

Host 拥有传输与生命周期。策略拥有请求内容与业务决策。SelfLoop 仍在本地调用策略。

## 诊断与验证

被拒绝的上下文使用 `INSTANCE_SNAPSHOT_MISMATCH` 与稳定的 `reason`，如 `ENVELOPE_SCHEMA`、`ROLE_REFERENCE`、`CARD_SKILL`、`REGISTRY_CARD_DRIFT` 或 `REGISTRY_NAME_COLLISION`。在已校验数据能定位时，附带任务 ID、角色 ID、实例 ID 与绑定组。成功与拒绝日志使用 `[RoleDispatch]` / `[RoleHost]` 与执行 ID，不记录证明、密钥或原始校验载荷。错误经 SDK 事件与 SSE 返回，并持久化为失败执行记录。

Host 验收日志与快照校验之后的拒绝包含已校验调用方 ID 与范围。此前的拒绝将这些值标记为 `unverified`；自称的身份字段绝不作为可信审计数据。证明失败保持同样的公开 `UNTRUSTED_SOURCE` 响应。内部日志额外以 `diagnostic_reason` 区分 `MALFORMED_PROOF`、`INVALID_SIGNATURE`、`EXPIRED_PROOF` 与 `FUTURE_PROOF`。新鲜度诊断仅在签名校验通过后给出。密钥错误与内容被改均产生 `INVALID_SIGNATURE`，无法可靠区分。该内部诊断不进入事件载荷与异常文本。

任务映射日志同时包含中心与 SDK ID。映射失败在 SDK 任务结果中保留 `INSTANCE_SNAPSHOT_MISMATCH` 与 `error_details.reason=SDK_TASK_MAPPING`。

派发时失败使用 `ROLE_DISPATCH_FAILED` 与 `error_details.reason` 判别符：`EXTENSION_UNKNOWN_ACTIVATED`、`EXTENSION_UNSUPPORTED`、`EXTENSION_NOT_ACTIVATED`、`EXTENSION_PAYLOAD_MISSING`、`AUTH_CREDENTIALS_MISSING`、`AUTH_METHOD_UNSUPPORTED`、`AUTH_PROVIDER_UNSATISFIED`、`AUTH_HEADER_CONFLICT` 或 `DISPATCH_FAILED`（登录、令牌交换与网络失败不按异常文本细分）。details 携带执行 ID 与原始任务、实例标识；回调无法映射时仅报告执行 ID。`error_type` 记录异常类名；异常消息与认证响应绝不进入错误或日志。

在仓库根目录运行定向验证：

```powershell
python -m pytest tests/test_host_role_snapshot.py tests/test_host_role_task_mapping.py tests/test_role_review_regressions.py tests/test_dependency_boundaries.py -q
```

测试启动并停止真实的本地 Host 与 worker HTTP A2A 服务。它们覆盖：模板不变的跨局点路由、同范围替换、技能转换、混合实例任务、本地 SelfLoop、真实的旧登录/Bearer 交换、经 SSE 的注册表漂移拒绝与失败记录、以及三个执行 API 的认证请求传播。一条闭环经真实传输派发三类扩展候选：认证 worker（真实登录交换，每条业务请求带 Bearer 头）、required Task-T worker（激活 URI、metadata 载荷、在 worker 断言 `A2A-Extensions` 头）与多接口 worker（注册钉选端点收到全部请求，更高协议版本的兄弟端点零请求）。一条中心全链路闭环经真实编排中心路径——目录与注册表文件、实时投影、派发 SSE 与执行记录——驱动相同候选，同一执行内混入旧实例任务；另一条链断言无凭据的角色候选被 `AUTH_CREDENTIALS_MISSING` 拒绝，保留原始任务标识且零业务请求。单元覆盖补充 Provider 输出验证（非空值、Bearer 格式、大小写不敏感头名、按要求的组合、自定义约定）、要求备选的凭据前置检查、协商回复守卫，以及旧任务与无认证派发的直通语义。Provider 头合并闭环断言：凭据与 Provider 的大小写冲突以零业务请求中止派发；同值去重为单条线上头；合法小写 Provider 头照常认证请求；后续闭环再从凭据 `auth_header` 配置、以及备选声明仅头名大小写不同的已配置 scheme 推导生效头，各含同值单头通过与异值拒绝；再从配置备选前的不完整 AND 组——被跳过组的配置不得将其拼写强加给 SDK 实际采用的 scheme——以及组内成员共享同一大小写不敏感头名的要求（零登录零请求结构化拒绝）推导。无需 LLM 或外部注册表。回归用例还覆盖 PSOP 字符串边界、AllSuccess/AnySuccess 步骤中的相同并发任务、事件/回调顺序、执行隔离、取消与派发前映射失败。API 传输验证与真实 A2A 执行另行测试；模拟的 API 成功不认证业务能力。

两个独立的合成实例支持手工检查：在仓库根目录运行 `python -m samples.role_pilot.technical_server`，默认监听本机 18991/18992（`--port-a`/`--port-b` 可改端口），与 `samples.start_agents_server` 分开运行，不注册注册表、不调用 LLM、不访问现网。technical-a（卡片 `Technical RAN A`，技能 `explore-a`/`Explore A`，范围 `technical-demo/city-a/ran-a`）与 technical-b（`city-b`/`ran-b`）按范围与技能路由；向 `http://127.0.0.1:18991/message:send` 发送带 `Content-Type: application/json` 与 `A2A-Version: 1.0` 的 POST，parts 文本为 `{"tenant":"technical-demo","site":"city-a","business_object":"ran-a","skill_id":"explore-a"}`，成功返回完成状态与包含 instance_id、agent_name、scope、skill_id、technical_only 的 JSON 文本 artifact；范围或技能不符返回失败状态。该响应仅为路由证据，不包含真实节能评估结果。

生产准入、按用户对象授权、数据库模式验收与业务能力认证不属于本技术试点。超出凭据文件与 `AuthProvider` 注入的新认证方式（如 mTLS），以及超出 Task-T 的扩展，不在当前受支持集合内。
